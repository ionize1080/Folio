# PDF 编辑瓶颈、改动与验证：2.6.0

本轮从识别、字体准备、排版、写入、后台调度和发布验证六个环节改进。覆盖 32 份文件、95 页，303 次编辑成功，136 次明确记录为受限；没有出现完整性断言失败，全部原文件的 SHA-256 保持不变。受限操作没有计入成功。尚未开展与 Acrobat、PDF-XChange、Foxit 相同文件、相同操作的对照测试，因此不能据此宣称全面达到或超过它们。

## Adrian Day 段落为何报错

这份黄金新闻由 Chromium 生成。第 2 页开头的 `A` 比原裁剪边界多出约 0.266 pt，旧逻辑因此把它排除在可编辑文字之外。段落选择缺少这个字后，保存阶段发现标签范围不完整，报出“需选择完整 MCID 范围”。截图中的首字母遗漏和保存失败由同一问题引起。

现在允许已经在原文中观察到、最多 1 pt 的矩形边界小幅越界，实际 PDF 裁剪路径保持不变；新增字形仍须符合验证后的范围。检查也能识别 `/NonStruct` 下的真实段落所有权，并在符合条件时替换同一标签中的连续局部文字。真实界面测试已完成选择、添加“测试测试”、保存、重新打开及再次识别为完整段落的全过程。

## 架构与代码瓶颈

| 环节 | 原因 | 本轮改动 | 验证与边界 |
| --- | --- | --- | --- |
| 段落识别 | 仅依赖几何间距时，生产者标签信息丢失，链接下划线又容易被当成分隔线 | 把紧凑的段落所有权信息传入单页检查；在分栏、单元格边界内优先使用经过验证的 P/H 标签；识别紧贴上一行的短下划线 | 不合并不同段落所有者；真实分隔线仍能分段 |
| 字体推荐 | 不同缺字集合重复对本机字体评分 | 采用稳定、分散的原字形样本；持久缓存评分；每次按实际缺字重新做覆盖检查 | 排名跨进程复用；缓存损坏时重算；所有候选仍参与评分 |
| 字体准备 | 全量 CJK 字形解码、字体集合导出、浏览器格式转换反复执行 | 按索引读取轮廓数量和字宽；延迟读取字体表；缓存已验证的完整字体和浏览器字体程序 | Latin、CJK 覆盖集合与完整 FontTools 解码结果一致；保留原子写入和元数据校验 |
| 编辑入口 | 备用大字体排在原嵌入小字体之前，原文已覆盖时仍等待备用字体 | 原字体、推荐、内置备用字体分队列；已覆盖原文先进入编辑；实际缺字才等待所需字体 | 慢备用字体、重开编辑器及真实界面测试 |
| 后台分析 | 整页拷贝可能把大量图像一起载入，后台评分又与前台争用资源 | 单个低优先级进程，逐页只复制字体资源；空闲调度、前台抢占、来源句柄租约、有限重试、缓存去重 | 工作单元结束后超过 256 MiB 则回收进程；这是回收阈值，不是严格峰值内存上限 |
| 原位写入 | 每个字形一次 `insert_text`、资源处理和内容流写入；样式逐字线性查找 | 字体注册一次，按字位批量写入一个内容流；单调推进样式游标 | 与参考绘制像素一致；覆盖旋转、连字、粗斜体、缩放、字距 |
| 嵌入 Type3 字体 | 单色矢量字形被当成无法解析的字体 | 从支持的 CharProc 路径恢复 OpenType CFF，保留 Unicode、变换和字宽；合并经验证的同名字体子集 | 保持原始字位；不把彩色、图像或复杂裁剪程序冒充普通轮廓 |
| 溢出保存 | 允许文字溢出时，排版引擎生成的框架裁剪仍切掉字形，重开后段落碎裂 | 仅在允许溢出时去掉新生成文字框架的裁剪；原文/Form 的裁剪继续独立验证 | 长单词与银行标准样本保存、重开文字完整 |
| 密集表格 | 每个对象反复遍历所有单元格 | 有界空间网格查询；大矩形走回退路径；保留原遍历顺序 | 与穷举结果做随机等价验证，保留列与单元格所有权 |

编辑路径依次尝试保留原字位、只重排受影响的原行、使用完整排版引擎。文字来源、实际字形范围、语义标签、分栏、表格和其他绘制对象分别校验。这样可以放宽误判造成的阻拦，同时避免为消除报错而删除周围内容。

## 性能实测

以下是同一台机器的单次对照，字体评分使用新缓存，两个请求运行在独立进程；完整字体程序可能已有缓存。字形写入时间不含整个文档的序列化。

| 操作 | 首次/逐字路径 | 复用/批量路径 |
| --- | ---: | ---: |
| 同一字体换一组缺字后的推荐 | 7,278 ms | 432 ms |
| 选定本机字体 | 702 ms | 70 ms |
| 浏览器字体准备 | 1,492 ms | 289 ms |
| 500 个字形写入 | 299 ms，500 个内容流 | 13 ms，1 个内容流 |

冷评分仍需数秒，因此后台预分析有实际价值。测试语料中的成功编辑，排版中位数为 130 ms，保存为 1,011 ms，重新检查为 1,285 ms；这是四个测试进程并行时的结果，不是逐键交互延迟，也不是所有文件的性能保证。

没有为加速而直接重写成 Rust/WASM：当前已确认的主要浪费是重复解析、重复评分、逐字调用和重复空间扫描。先消除这些工作，比只改变语言更直接。大的保存操作仍会克隆/重写文档结构，后续需要独立验证增量提交与更紧凑的字形传输协议。

## 行业资料的可借鉴部分

[BabelDOC 排版文档](https://funstory-ai.github.io/BabelDOC/ImplementationDetails/Typesetting/Typesetting/)采用保留原组件、排入原框、扩展空间、调整间距/缩放的层次。这与区分不变原文几何和变更文本的方向一致，适合借鉴局部重排及布局约束；它主要解决翻译后的长度变化，不等于交互式编辑性能证明。本版也不会为了塞进原框而静默缩小用户选定字号。参见[作者论文](https://arxiv.org/abs/2605.10845)。

[Acrobat 文档](https://experienceleague.adobe.com/en/docs/document-cloud-learn/acrobat-learning/get-started/edit/auto-adjust-layout)描述了带适用限制的跨页自动重排；本版尚未实现该能力。[PDF-XChange](https://help.pdf-xchange.com/pdfxe10c/adding-and-editing-document-text_ed.html)区分文本块与单个文字元素编辑，[Foxit SDK](https://developers.foxit.com/documents/development-guide/pdf-sdk-web/features/the-edit-modules.html)公开了编辑模块和字体相关接口。这些公开资料可用于比较行为，不能当作其专有识别算法的完整说明。

## 测试台账与尚未解决的问题

32 份文件包含 15 份自有样本和 17 份公开样本，每份随机抽取最多 3 页，新闻回归固定包含第 2 页。检查覆盖保存文字、重开后段落、编辑区域之外像素、相邻页像素、页数和文字来源唯一性。图像保持不变不代表图像语义识别准确率已被测量；本轮也没有新增学习型表格/图像识别模型。

台账位于 `D:\APP\PDF Samples\_folio-tests\editing-ledger.jsonl`。新计划默认按 SHA-256 排除已经测试过的文件；指定 `--reuse-files` 才允许从旧文件选取未测试页。修复后复测同一计划是有意的回归验证。已验证下一轮 32 份文件与本轮无重复。

公开样本使用固定 URL/版本和 SHA-256，Actions 分四路下载验证；自有 PDF 和完整私有报告没有进入 GitHub。发布还要求六路引擎回归、真实界面操作、最终包资源匹配及包内引擎检查通过，所有结果须对应同一提交和工作流。

136 次受限尝试主要涉及交错覆盖绘制、链接/替代文字等复杂标签、部分 MCID 范围、特殊字体映射与独立注音。完整分类和逐文件统计见[汇总台账](editing-260-local-results.json)。这些需要更细的字形、标签和批注范围搬移方案，当前保留明确原因与草稿，不能将其计为已修复或成功编辑。
