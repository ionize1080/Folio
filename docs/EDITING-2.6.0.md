# PDF editing architecture and verification, 2.6.0

This work targets observable editing correctness and latency. It does not establish parity with Acrobat, PDF-XChange or Foxit: a controlled, identical-operation competitor benchmark has not been run. Sources below describe publicly documented behavior, not proprietary internals.

## Findings and changes

| Stage | Observed bottleneck or defect | Change | Verification |
| --- | --- | --- | --- |
| Source ownership | A Chromium line clip overhung the initial `A` by about 0.266 pt. The visible letter was excluded, then the MCID completeness check rejected the paragraph. | Admit up to 1 pt of **observed original** rectangular overhang. The real clip is unchanged; new ink must remain inside the certified envelope. | Actual Adrian Day paragraph, UI input/save/reopen; generated clipped text; genuinely new clipping remains rejected. |
| Tagged paragraphs | `/NonStruct` inline nodes and lost ParentTree evidence in bounded page inspection discarded real paragraph ownership. | Carry compact MCID-to-paragraph hints into single-page inspection. Prefer validated P/H owners within existing column/cell boundaries. | Two save cycles preserve ParentTree; different paragraph owners remain separate. |
| Local tagged edits | Some producers put several visual blocks inside one MCID. The complete-scope rule blocked even local replacement. | Allow a contiguous subset only when original text matches selected source objects and replacement stays inside the existing MCID wrapper after ET. | Generated partial-scope save preserves neighbouring pixels; forged/incomplete source selections still fail. |
| Paragraph boundaries | Inline hyperlink underlines looked like horizontal section rules. | Recognize a short rule immediately below, and contained within, the previous text line as decoration. | Inline underline joins; separated section rule still divides. |
| Embedded fonts | Chromium Type3 outline subsets were treated as unresolved fonts. | Reconstruct monochrome vector char programs as OpenType CFF, retaining Unicode, transforms and advances; combine verified sibling subsets. | Generated Type3 edit, identical anchors, bounded raster edge differences and preserved untouched-page pixels. Unsupported image/color/clip programs remain explicit. |
| Font recommendation | Each changed missing-character set could rescore installed fonts. | Stable distributed source-glyph evidence; content/catalog-keyed disk rankings; exact required-character coverage filtering per request. | Warm rankings survive process-cache clearing; every requested character is checked; corrupt cache entries recompute. |
| Font preparation | Full CJK outlines and font collections were repeatedly decoded, serialized and sanitized across processes. | Lazy face extraction, indexed contour/advance checks, validated browser-font cache, deterministic timestamps and atomic metadata publication. | Indexed coverage equals the full FontTools decoder for Latin and CJK; concurrent publication regressions. |
| Background work | On-demand scoring blocked font interactions; copying pages for warming could copy large images. | Low-priority, single-worker idle scheduling; font-only resource discovery; foreground preemption; leased sources; bounded retries/cache; recycle after a measured 256 MiB work unit. | Scheduler cancellation/deduplication/lease tests; real font scanning. Memory threshold is a recycle threshold, not a hard peak-RSS cap. |
| Fast entry | Emergency CJK preparation queued ahead of small embedded fonts and paragraph entry awaited unused fallback faces. | Separate low-priority fallback preparation, idle worker shutdown, and activate covered original text without awaiting unused emergency fonts. | Slow-fallback/reopened-editor tests and real UI regression. |
| Native layout | One `insert_text` call, resource operation and stream per glyph; linear style search per glyph. | Batch positioned glyphs into one content stream, preserving ActualText and explicit matrices; monotonic style cursor. | Pixel equality against reference drawing, ligatures, rotations, synthetic styles, spacing and CJK wrapping. |
| Generated overflow | Story's layout-frame clip cut overhanging glyphs even when overflow was enabled; reopened paragraphs fragmented. | Remove only generated text-layout clips when overflow is allowed. Validate inherited document/Form clips independently during save. | Long-token regression and the bank-standard sample; exact reopened text. |
| Dense tables | Repeated object × cell scans inflated grouping work. | Bounded spatial bins with stable input-order lookup; large rectangles use a bounded fallback. | Randomized exhaustive-equivalence tests, cell ownership and column regressions. |

The editor follows a local hierarchy: retain exact anchors when possible, reflow affected original lines when needed, then use the shaping/layout engine. Source object signatures, glyph ink, tag ownership, columns, cells and foreign paint remain distinct constraints. This avoids making text extraction order the sole paragraph model.

## Public algorithms and product information

[BabelDOC typesetting documentation](https://funstory-ai.github.io/BabelDOC/ImplementationDetails/Typesetting/Typesetting/) describes preserving original components, reflowing changed Unicode text, trying the original frame, then expansion and fit adjustments. It also documents performance/layout limitations. Its translation-first approach is useful evidence for separating immutable source geometry from changed text. Folio retains that distinction but does not silently shrink the user's chosen font to fit an edit. Its translation results are not an interactive-editing benchmark. See also the authors' [BabelDOC paper](https://arxiv.org/abs/2605.10845).

[Acrobat auto-adjust layout](https://experienceleague.adobe.com/en/docs/document-cloud-learn/acrobat-learning/get-started/edit/auto-adjust-layout) documents reflow across pages and explicitly notes content/language limitations. Cross-page automatic reflow is not claimed for this Folio release.

[PDF-XChange's editing guide](https://help.pdf-xchange.com/pdfxe10c/adding-and-editing-document-text_ed.html) distinguishes block selection/editing from individual text-element editing. [Foxit's SDK editing guide](https://developers.foxit.com/documents/development-guide/pdf-sdk-web/features/the-edit-modules.html) exposes editing modules and font-related operations. These support providing different editing levels; neither discloses enough to reproduce its paragraph detector or establish relative quality.

## Test ledger and reproducibility

The local campaign selects 32 distinct PDFs and 95 pages from the existing sample collection, with a recorded random seed. The news regression always includes page 2. Every document is hashed before and after; original files are never overwritten. Each eligible page samples up to three paragraphs and tries replacement/insertion; the reported Adrian Day case additionally inserts `测试测试`.

Successful edits must pass saved-text, reopened-paragraph, outside-edit pixel, adjacent-page pixel, page-count and unique-source-ownership checks. Limitations are reported separately from successes and assertion failures. A scan/no-editable-prose page is not counted as a successful text edit. Raster checks use the original and saved PDF; synthetic regressions additionally exercise PDFium and vector anchors.

The append-only local ledger is `D:\APP\PDF Samples\_folio-tests\editing-ledger.jsonl`; future plans exclude previously tested files by SHA-256. `--reuse-files` explicitly permits their untested pages. Re-testing the same planned pages after a fix is deliberate regression verification. The selected files already existed, so this campaign adds no duplicate downloads to the user's collection.

`tests/public-editing-260.json` pins 17 public inputs by URL/hash and page sample. Four independent Actions lanes download only those public inputs, verify hashes, record each limitation, require per-document success floors, and pass commit/run-bound reports to publication. Private input PDFs and full private reports are not committed. Local aggregate results are in `docs/editing-260-local-results.json`.

Useful commands: `python tests/editing-corpus-260.py --plan tests/output/next-editing-plan.json --count 32 --seed 20261112`, then `--run tests/output/next-editing-plan.json --workers 4`. The plan preserves the random selection for reproducible retries. `python tests/editing-260-public.py --shard 1` runs the first public lane. A failed worker cannot reuse an earlier successful report.

## Measured scope and remaining work

`tests/editing-260-performance.py` records fresh-process recommendation, font selection and browser preparation separately. The final measurement reduced recommendation from 7,278 ms to 432 ms across independent processes with identical ranking evidence; a 500-glyph write reduced 299 ms/500 streams to 13 ms/one stream. Font selection measured 702/70 ms and browser-font preparation 1,492/289 ms in those two processes. These are local measurements, not universal latency guarantees; full cold scoring still costs seconds and is moved into idle work. These measurements include the indexed-font optimizations. The 32-file campaign recorded 303 successful edits, 136 explicit limitations and zero assertion-failing files; all original hashes were unchanged.

Remaining limits include replacement across multiple link/alternative-text semantic owners, text interleaved with overlapping foreign paint, unsupported embedded encodings, some complex-script mappings and independent ruby annotations. They remain visible in the ledger. A faithful source-preserving splice for these cases requires range-level glyph/annotation relocation, not removing checks wholesale. This release also does not introduce a new learned table/image detector or OCR model. Image/page preservation is tested; recognition accuracy is not inferred from absence of crashes.

Large-document saves still clone/rewrite document structures. Incremental source-object commits and a compact binary glyph transport are future architecture work. Before adding Rust/WASM, profile these specific paths against the native parsing/writing work that remains; another language alone does not remove duplicated work or IPC serialization.
